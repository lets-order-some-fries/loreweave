## AREA: Graph-based retrieval for knowledge bases (2024-2026): HippoRAG family, GraphRAG family, tree-based and relation-free successors

### HippoRAG (NeurIPS 2024) (2024-05)
Source: https://arxiv.org/abs/2405.14831
Models hippocampal indexing theory: an LLM does schema-free OpenIE over passages to build a KG of phrase nodes with relation edges plus embedding-based synonym edges; at query time, named entities extracted from the query seed Personalized PageRank (PPR) over the graph, and passages are ranked by aggregated PPR scores of the phrases they contain. Beats prior SOTA multi-hop retrieval by up to 20% on MuSiQue/2Wiki/HotpotQA in a SINGLE retrieval step, matching iterative methods like IRCoT while being 10-30x cheaper and 6-13x faster at query time. Cost is concentrated at indexing (one OpenIE LLM pass per passage); query time needs only entity extraction + one PPR run. Fully local-feasible: the reference implementation uses an in-process graph (igraph) and pluggable vector stores, no graph DB required.

### HippoRAG 2 (ICML 2025) (2025-02)
Source: https://arxiv.org/abs/2502.14802
Fixes HippoRAG 1's weakness on simple factual QA via 'dense-sparse integration': the KG now contains both phrase nodes (sparse/conceptual) and passage nodes (dense/contextual) linked by contains-edges; queries are embedded against whole triples (not just entities), an LLM 'recognition memory' filter prunes candidate triples (one cheap query-time call), and both filtered phrase seeds AND dense-retrieval-scored passage nodes get PPR reset probability. Result: +7 F1 on associative/multi-hop tasks over the best embedding model (NV-Embed-v2, e.g. MuSiQue F1 44.8→51.9, 2Wiki R@5 76.5→90.4) while matching embedding retrievers on simple QA — where RAPTOR/GraphRAG/LightRAG lose 5-10 F1. Indexing reported at ~9M LLM tokens on MuSiQue vs ~115M for GraphRAG-style summarization pipelines. Repo (OSU-NLP-Group/HippoRAG) runs fully locally with vLLM + Milvus Lite/parquet files; the graph is in-process — SQLite-scale friendly.

### Microsoft GraphRAG 'From Local to Global' (2024) (2024-04)
Source: https://arxiv.org/abs/2404.16130
Targets global sensemaking queries ('main themes of the corpus') that vector RAG cannot answer: LLM extracts an entity/relationship graph from 600-token chunks (with self-reflection 'gleaning' passes), hierarchical Leiden community detection partitions it (levels C0-C3), and an LLM pre-writes a summary report per community; querying is map-reduce over community summaries with 0-100 helpfulness scoring. Wins 72-83% on comprehensiveness/diversity vs vector RAG on ~1M-token corpora, and root-level summaries need 9-43x fewer query tokens than full-text summarization. Cost is the catch: indexing is extremely LLM-heavy (multiple calls per chunk plus all community reports), global search burns hundreds of thousands of tokens per query, and community hierarchies must be rebuilt on updates. Feasible without a graph DB (the official implementation uses parquet + in-memory graphs), but the LLM spend, not the infrastructure, is the barrier for personal use.

### LightRAG (2024) (2024-10)
Source: https://arxiv.org/abs/2410.05779
Lightweight GraphRAG alternative: LLM extracts entities/relations per chunk into key-value profiles on graph nodes/edges with dedup, and retrieval is dual-level — the LLM extracts low-level (entity) and high-level (theme) keywords from the query, vector-matches them to nodes/edges, and gathers one-hop neighbors. Beats naive RAG heavily and edges out GraphRAG (~52-53% win rates) on LLM-judged comprehensiveness/diversity, with query cost <100 tokens + 1 API call vs GraphRAG's ~610K tokens per global query; supports incremental graph-merge updates with no community rebuild. Caveats from later evaluations: GraphRAG-Bench found it degrades simple-QA accuracy and E2GraphRAG measured its retrieval up to 100x slower than optimized pipelines. Ships with file/nano-vectordb storage — trivially local; still requires one LLM extraction pass over every chunk at index time.

### RAPTOR (ICLR 2024) (2024-01)
Source: https://arxiv.org/abs/2401.18059
Recursive summarization tree, no entity graph: 100-token chunks are embedded (SBERT), softly clustered with UMAP+GMM (BIC model selection), each cluster is LLM-summarized, and the process recurses on summaries until clustering fails. The winning retrieval mode is 'collapsed tree' — flatten all layers into one vector index and take top nodes to a 2,000-token budget — which means at inference it is just vector search over an augmented index. Gains are largest on holistic, long-document understanding: QuALITY 82.6% (vs 62.3% prior SOTA with GPT-4), QASPER 55.7 F1 vs DPR 53.0; 18.5-57% of retrieved nodes come from summary layers. Build cost scales linearly (~28% extra tokens as summaries); GraphRAG-Bench later found it the most faithful method for creative/synthesis tasks but weak on evidence coverage. The easiest architecture on this list to implement locally — pure embeddings + clustering + one summarizer, SQLite-native.

### LazyGraphRAG (Microsoft, 2024-11; shipped in Azure/Microsoft Discovery 2025) (2024-11)
Source: https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/
Deletes GraphRAG's expensive index: concepts come from NLP noun-phrase extraction (no LLM), edges from co-occurrence, communities from graph statistics — indexing cost equals plain vector RAG, 0.1% of full GraphRAG. All intelligence moves to query time: LLM expands the query into subqueries, chunks are ranked best-first, a cheap LLM does sentence-level relevance tests under an explicit budget (z=100/500/1500) with iterative deepening into sub-communities, then claims are extracted from relevant chunk groups and assembled. At z=500 it significantly outperforms vector RAG, GraphRAG global/local, and RAPTOR on BOTH local and global queries at ~4% of GraphRAG global's query cost (700x cheaper than C2 global search). The strongest existence proof that deferred, budgeted query-time LLM work over a cheap statistical graph beats expensive index-time summarization — and the whole design is local-first friendly.

### Fast-GraphRAG (Circlemind, open source) (2024-11)
Source: https://github.com/circlemind-ai/fast-graphrag
Production OSS reinterpretation of HippoRAG's idea: LLM entity/relation extraction builds a navigable graph, retrieval runs PageRank-based graph exploration, and incremental insertion is first-class. Claims 6x cost reduction vs Microsoft GraphRAG on the same corpus ($0.08 vs $0.48 on The Wizard of Oz), async Python, runs 'at scale without heavy resource requirements' — plain pip install, embedded storage, no graph database. Notable as evidence that PPR-style retrieval is the mechanism practitioners kept when optimizing GraphRAG for cost.

### KET-RAG (KDD 2025) (2025-02)
Source: https://arxiv.org/abs/2502.09304
Multi-granular indexing that answers 'where should scarce LLM extraction budget go': build a full LLM-extracted KG 'skeleton' only for the most important text chunks (selected by centrality), and index everything else with a near-free text-keyword bipartite graph; retrieval runs GraphRAG-style local search on the skeleton while mimicking it on the bipartite graph. Matches or beats Microsoft GraphRAG retrieval quality with indexing cost reduced by over an order of magnitude, and improves generation up to 32.4% in its evaluations. Directly applicable pattern for a personal vault: spend LLM extraction only on hub notes, use keyword/entity co-occurrence for the long tail.

### PathRAG (2025) (2025-02)
Source: https://arxiv.org/abs/2502.14902
Attacks redundancy rather than recall: after keyword-based node retrieval, a flow-based pruning algorithm with distance-aware decay (α) and early stopping (θ) extracts the most reliable relational PATHS between retrieved node pairs, converts each path to text, and orders paths by reliability in the prompt (best path last, exploiting LLM recency). Wins ~60% vs GraphRAG and ~57% vs LightRAG across six datasets on LLM-judged quality, attributing gains to feeding the generator coherent paths instead of flat noisy subgraphs. Pruning is O(N²/(1-α)θ) over only the 10-60 retrieved nodes — negligible compute, easily done in-process on any graph representation.

### NodeRAG (2025) (2025-04)
Source: https://arxiv.org/abs/2504.11544
Argues graph STRUCTURE design is the neglected variable: a seven-type heterograph (text chunks, LLM-paraphrased 'semantic units', attributes, high-level elements, relationship nodes, plus entity-name and overview nodes as entry-points only), unifying RAPTOR-style summaries and HippoRAG-style entities in one graph. Retrieval = dual entry (exact match on entity/title nodes + HNSW vector search on content nodes) then SHALLOW personalized PageRank (α=0.5, only 2 iterations) to find cross nodes, returning only retrievable types. Beats GraphRAG/LightRAG/HippoRAG on multi-hop QA (HotpotQA 89.5%, MuSiQue 46.3%) with fewer retrieved tokens (~5K), and is cheaper on every axis: indexing ~21-25 min vs GraphRAG's 50-76, storage 117-250MB, query 4-9s. Demonstrates that 2-iteration PPR suffices — a few sparse matrix multiplications, trivially SQLite/NumPy-scale.

### MiniRAG (2025) (2025-01)
Source: https://arxiv.org/abs/2501.06713
Graph RAG designed for on-device small language models: a semantic-aware heterogeneous graph combines text chunks and named entities in one structure, and a topology-enhanced retrieval leans on graph structure to compensate for the weak semantic understanding of SLMs. Achieves performance comparable to LLM-based RAG while using SLMs and only ~25% of the storage of prior systems. Directly relevant to local-first engines that must index/query with an Ollama-class local model rather than frontier APIs: graph topology substitutes for model capability.

### E2GraphRAG (2025) (2025-05)
Source: https://arxiv.org/abs/2505.24226
Efficiency-first hybrid: index-time work is a RAPTOR-like LLM summary tree plus an entity graph built with spaCy (no LLM relation extraction), with bidirectional entity-to-chunk indexes for O(1) lookup; at query time an adaptive strategy picks local (entity-based) vs global (tree-based) retrieval based on graph structure. Reports up to 10x faster indexing than GraphRAG and 100x faster retrieval than LightRAG with competitive QA quality. A concrete template for markdown-vault indexing: spaCy NER + summary tree covers both multi-hop and sensemaking with almost no index-time LLM spend.

### LinearRAG (ICLR 2026) (2025-10)
Source: https://arxiv.org/abs/2510.10114
Relation-free graph construction taken to its conclusion: LLM relation extraction is identified as the unstable, noisy, expensive step, so LinearRAG builds a hierarchical 'Tri-Graph' from lightweight entity extraction and semantic linking only — zero extra LLM token consumption at indexing, scaling linearly with corpus size. Retrieval is two-stage: relevant-entity activation via local semantic bridging, then passage retrieval via global importance aggregation (PageRank-flavored scoring). Significantly outperforms graph-RAG baselines on four datasets while being the cheapest indexer in its comparisons; from the same group as the Awesome-GraphRAG survey. Validates the co-occurrence-graph + importance-propagation recipe as the 2026 efficiency frontier.

### LeanRAG (AAAI 2026) (2025-08)
Source: https://arxiv.org/abs/2508.10391
Fixes the 'semantic islands' problem of hierarchical GraphRAG (community summaries have no relations between them, blocking cross-community reasoning): semantic aggregation clusters entities and creates explicit relations among aggregation-level summaries, forming a fully navigable multi-level network; retrieval is bottom-up — anchor on fine-grained entities, then traverse upward along the semantic pathways. Outperforms prior graph-RAG on four QA benchmarks while cutting retrieval redundancy 46%. Together with HiRAG (arXiv:2503.10150, GMM-clustered hierarchical entity layers bridging local and global knowledge), it defines the 2025-26 'hierarchy + explicit cross-links' branch of the design space.

### GraphRAG-Bench / 'When to Use Graphs in RAG' (ICLR 2026) (2025-06)
Source: https://arxiv.org/abs/2506.05690
The decisive comparative study: benchmarks MS-GraphRAG, LazyGraphRAG, HippoRAG 1+2, LightRAG, Fast-GraphRAG, and RAPTOR against vanilla RAG across four difficulty tiers. Findings: vanilla RAG WINS simple fact retrieval (61-88% evidence recall vs 49-70% for graph methods — graphs add noise); graph methods win complex multi-hop reasoning (HippoRAG family hits 87.9-90.9% evidence recall) and contextual summarization; RAPTOR is most faithful for creative synthesis. Cost per query diverges wildly: MS-GraphRAG global ~331K tokens, LightRAG ~100K, HippoRAG 2 ~1K, vanilla ~879 — i.e., HippoRAG 2 delivers graph-level reasoning at vanilla-RAG query cost. Conclusion: use graphs only where multi-hop/synthesis is needed, route simple queries to plain retrieval.

### AtomicRAG (2026) (2026)
Source: https://arxiv.org/abs/2604.20844
Newest evolution of the HippoRAG line: replaces both coarse chunks and rigid triples with 'knowledge atoms' — individual self-contained factual propositions — as graph nodes alongside entities, with entity edges simplified to mere existence-of-relationship (no relation labels) because 'triple-based entity linking is sensitive to relation-extraction errors' causing missing reasoning paths. Retrieval combines personalized PageRank with relevance-based filtering. Outperforms strong RAG baselines on five benchmarks in retrieval accuracy and reasoning robustness. Confirms two 2026 convergence trends: proposition-level granularity and unlabeled edges + PPR as the robust backbone.

### Ecosystem trackers: Awesome-GraphRAG and 2025 unified evaluations (2025-2026)
Source: https://github.com/DEEP-PolyU/Awesome-GraphRAG
The DEEP-PolyU curated list (survey, benchmarks, open-source projects) is the maintained map of this space and its group produced both LinearRAG and the GraphRAG survey. A separate 2025 Michigan State/Meta unified-protocol study found no universal winner: plain RAG edged single-hop lookup (F1 64.8 vs 63.0) while graph-guided retrieval led multi-hop (70.3 vs 67.0 on MultiHop-RAG) — corroborating GraphRAG-Bench's routing conclusion. Also notable in the 2026 wave: GRASP (agentic search over propositions, arXiv:2605.16598) and TagRAG (tag-guided hierarchical KG, arXiv:2601.05254), continuing the proposition-graph and hierarchy trends.

### DESIGN IMPLICATIONS
- Best quality/complexity ratio for a personal knowledge engine is the HippoRAG 2 recipe, simplified: passage nodes + entity/phrase nodes + synonym edges, query embedded against facts AND passages, dense scores used as Personalized PageRank reset probabilities. It is the only architecture in GraphRAG-Bench that wins multi-hop reasoning (~88-91% evidence recall) while staying at vanilla-RAG query cost (~1K tokens/query vs 331K for MS-GraphRAG) and NOT regressing on simple lookups — the dense-sparse fusion is what prevents the 5-10 F1 simple-QA penalty every other graph method pays.
- No graph database is needed at personal-vault scale. Every winning system runs PPR on an in-process graph (HippoRAG uses igraph + parquet/Milvus Lite; NodeRAG shows α=0.5, 2-iteration shallow PPR suffices). Concretely: SQLite tables for nodes/edges/chunks, sqlite-vec or brute-force cosine for embeddings (fine under ~100K chunks), FTS5 for exact entity match, and PPR as a few sparse matrix-vector multiplications in scipy/rustworkx — milliseconds on graphs with millions of edges. NodeRAG's full benchmark corpora fit in 117-250MB.
- Do NOT copy Microsoft GraphRAG's index-time community summarization. The 2025-26 evidence is unanimous: LazyGraphRAG matches/beats GraphRAG global quality at 0.1% indexing cost and 700x lower query cost by deferring all LLM work to query time; KET-RAG cuts indexing an order of magnitude; HippoRAG 2 indexes MuSiQue at ~9M tokens vs ~115M. Index-time LLM summarization of communities is the single worst quality-per-dollar component in the space and also breaks incremental updates.
- Skip LLM relation extraction; keep relation labels out of the graph. The 2025-26 convergence (LazyGraphRAG, LinearRAG, E2GraphRAG, AtomicRAG) is that relation extraction is the unstable, expensive step and that unlabeled edges (co-occurrence, entity-mention, existence-of-relationship) are sufficient for PPR-style retrieval — AtomicRAG explicitly shows labeled-triple linking CAUSES missing reasoning paths. Use spaCy NER/noun-chunks (free, local, fast) for entities; optionally apply KET-RAG's trick of spending LLM extraction only on the highest-centrality 'hub' notes.
- A markdown vault gives you the graph for free — exploit it. Wiki-links/backlinks, tags, folder hierarchy, and headings are exactly the entity-and-passage edges other systems pay LLMs to reconstruct. Treat notes/sections as passage nodes, [[links]] + shared spaCy entities + embedding-synonym edges (cosine ≥ ~0.8, HippoRAG 2's threshold) as the edge set, and you have a higher-precision graph than OpenIE would produce, at zero token cost.
- Add a RAPTOR-style summary layer for global/sensemaking queries ('what are the themes across my notes'), using collapsed-tree retrieval: cluster note embeddings (UMAP+GMM or even simpler), LLM-summarize each cluster, recurse, then just insert summary nodes into the same vector index — retrieval stays plain top-k, no traversal logic. Cost is linear, ~28% extra tokens, and RAPTOR's summaries are also what wins faithfulness on synthesis tasks. This is the cheapest path to GraphRAG-global capability.
- Route or fuse — never send everything through the graph. GraphRAG-Bench's core negative result is that graph retrieval UNDERPERFORMS vanilla retrieval on simple fact lookup (adds noise). Either classify queries (entity-lookup → vector/FTS5; multi-hop/relational → PPR; thematic → summary layer) or use HippoRAG 2's always-fused design where dense retrieval dominates when graph signal is weak. The fusion approach is simpler and degrades gracefully.
- Design for incremental updates from day one — a personal vault changes daily. Entity-graph architectures (LightRAG, fast-graphrag, HippoRAG) support node/edge-local merges on note edit; community hierarchies (GraphRAG) and summary trees (RAPTOR) require partial rebuilds. Practical compromise: incremental entity/passage graph updates immediately, lazy/batched re-clustering of the summary layer (e.g., nightly, only for dirty clusters).
- Adopt LazyGraphRAG's budgeted query-time compute model for local LLMs: iterative deepening with an explicit relevance-test budget (z) lets a small local model spend more inference only on hard queries, giving a tunable cost-quality dial instead of fixed pipeline cost. MiniRAG independently shows graph topology compensates for small-model weakness — important if the engine must work offline with Ollama-class models (~25% storage of standard pipelines).
- Compress and de-noise what reaches the generator: PathRAG (paths, not subgraphs; best evidence last in the prompt) and LeanRAG (-46% retrieval redundancy) show redundant flat context measurably hurts generation. Return a small set of passages plus the connecting facts/paths, and consider HippoRAG 2's 'recognition memory' step — one cheap LLM call filtering candidate facts before PPR — as the highest-leverage query-time LLM use.
- Concrete recommended architecture (best quality/complexity): SQLite (chunks, entities, edges, FTS5) + embedded vectors; indexing = markdown parse → blocks/sections as passages → spaCy entities + wiki-links + synonym edges (no LLM required; optional LLM atoms/OpenIE for hub notes only) → optional nightly cluster summaries; retrieval = query embedding → top facts + top passages → optional 1-call fact filter → 2-iteration PPR with dense reset probabilities → top-k passages (+paths) under a token budget. This combines HippoRAG 2 (fusion + PPR), LinearRAG/LazyGraphRAG (relation-free cheap indexing), KET-RAG (selective LLM spend), NodeRAG (shallow PPR), and RAPTOR (collapsed summary layer) — each choice backed by a 2025-26 result.
- Evaluation caution when tuning: LightRAG/PathRAG-style 'win rates' are LLM-judged comprehensiveness/diversity contests that reward verbosity; prefer recall-based metrics (evidence recall@k, as in GraphRAG-Bench and HippoRAG 2) on a held-out set of your own multi-hop questions over vault content. Expect the graph layer to pay off only on genuinely associative queries — measure that slice separately or the graph will look useless on average.

## AREA: Production agent-memory systems and their data models (2024-2026): Letta/MemGPT, Mem0, Zep/Graphiti, MemOS, LangMem, Cognee, A-Mem, and the LoCoMo/LongMemEval benchmarks

### MemGPT — OS-inspired virtual context management (2023-10 (foundational for the 2024-26 wave))
Source: https://arxiv.org/abs/2310.08560
Treats the context window as RAM and external storage as disk: main context = system instructions + a writable 'working context' + a FIFO message queue; external context = recall storage (full conversation log) and archival storage (arbitrary text, vector-indexed). The agent self-edits memory via function calls (core_memory_append/replace, archival_memory_insert/search, conversation_search), is warned on 'memory pressure' as the queue fills, and evicted queue messages are recursively summarized. Memory units are unstructured text strings; there is no contradiction handling — updates simply overwrite working-context text.

### Letta memory blocks — the production data model of MemGPT (2024-2026 (ongoing))
Source: https://docs.letta.com/guides/agents/memory-blocks
The core memory unit is a 'block': {label, value, description, character limit}, persisted in a database, addressable by ID, and compiled into the prompt inside <memory_blocks> XML — always in context, no retrieval needed. The description field is what tells the agent how to read/write the block. Blocks can be shared by ID across multiple agents (shared memory as a multi-agent coordination primitive) and can be read_only. Updating = in-place rewriting by the agent's memory tools; history lives only in recall/archival storage, not in block versioning.

### Letta sleep-time compute — background memory reorganization (2025-04)
Source: https://arxiv.org/abs/2504.13171 and https://www.letta.com/blog/sleep-time-compute/
A second 'sleep-time agent' shares memory blocks with the primary agent and, while the primary is idle, transforms 'raw context' into 'learned context' — rewriting, compressing, and pre-deriving inferences so answers are cheaper at test time. Paper shows ~5x reduction in test-time compute for equal accuracy and up to +13-18% accuracy on stateful GSM/AIME tasks. The primary agent may lack memory-editing tools entirely; only the sleep agent writes memory, and it can run a bigger/slower model than the chat agent. This is the strongest production argument for asynchronous consolidation as a first-class architectural role.

### Mem0 — two-phase extraction/update pipeline with ADD/UPDATE/DELETE/NOOP (2025-04)
Source: https://arxiv.org/abs/2504.19413
Extraction: an LLM receives (running conversation summary S, last m=10 messages, the new message pair) and emits salient candidate facts in natural language. Update: for each candidate, retrieve top s=10 semantically similar existing memories and let the LLM choose via tool call: ADD (no equivalent exists), UPDATE (augment existing), DELETE (contradicted), NOOP. The memory unit is a natural-language fact with embedding + timestamps. On LoCoMo it beat LangMem/Zep on most categories with ~7k tokens per query vs 26k full-context (91% lower p95 latency); its weakness is that DELETE physically discards history — no temporal record of what was believed before.

### Mem0^g — graph variant with 'mark obsolete, don't delete' (2025-04)
Source: https://arxiv.org/abs/2504.19413 (Section on Mem0-g)
A two-stage LLM pipeline extracts typed entities then relationship triplets (v_s, r, v_d); nodes carry entity type, embedding, and creation timestamp. Crucially, its conflict handler differs from base Mem0: when new information conflicts with existing edges it marks them invalid rather than physically removing them, 'to enable temporal reasoning.' Retrieval is dual: entity-centric (match query entities to nodes, expand incoming+outgoing edges) and semantic-triplet (embed whole query, threshold-match against triplet embeddings). Mem0^g won the temporal-reasoning category on LoCoMo (J=58.13 vs OpenAI memory 21.71).

### Zep/Graphiti — bi-temporal knowledge graph with edge invalidation (2025-01)
Source: https://arxiv.org/abs/2501.13956 and https://github.com/getzep/graphiti
Three subgraph tiers: episode subgraph (raw messages/text/JSON — a non-lossy ground-truth store), semantic entity subgraph (LLM-extracted, deduplicated entities plus fact edges), and community subgraph (label-propagation clusters with summaries, incrementally updated by assigning new nodes to the plurality community of their neighbors). Every edge carries four timestamps: t_created/t_expired (transaction time — when the system learned/superseded it) and t_valid/t_invalid (valid time — when the fact held in the world). On contradiction, the affected edge's t_invalid is set to the invalidating edge's t_valid — invalidated, never deleted — enabling point-in-time queries. Retrieval fuses cosine similarity + BM25 + breadth-first graph traversal, reranked with RRF/MMR/episode-mention-frequency/cross-encoder; on LongMemEval it beat full-context gpt-4o by 18.5% (71.2% vs 60.2%) at ~90% lower latency using 1.6k vs 115k tokens.

### MemOS — memory as an OS-managed resource; the MemCube unit (2025-07)
Source: https://arxiv.org/abs/2507.03724
Unifies three memory forms — plaintext (external editable knowledge), activation (KV-cache), and parametric (weights/adapters) — with explicit transformation paths: hot plaintext compiles into KV templates for fast decoding, stable cross-task knowledge distills into parameters, cold parameters offload back to plaintext. The unit is the MemCube: payload + metadata in three groups — descriptive (timestamp, origin signature, semantic type), governance (access control, TTL/decay, priority, compliance tags), and behavioral usage indicators (access frequency/recency = hot/cold, contextual fingerprint, version chain of modification history and derivation lineage). Lifecycle states: generated → activated → merged → archived → expired, transitioned by access patterns and time decay; MemOS-0630 ranked first in all LoCoMo categories vs Mem0, LangMem, Zep, OpenAI-Memory.

### LangMem — profiles vs collections; hot-path vs background formation (2025-02)
Source: https://langchain-ai.github.io/langmem/concepts/conceptual_guide/ and https://www.langchain.com/blog/langmem-sdk-launch
Three memory types (semantic/episodic/procedural) with two semantic representations: a profile (one schema-validated JSON document, continuously patched — best when only latest state matters) versus a collection (unbounded individual records, where 'the system must reconcile new information with previous beliefs, either deleting/invalidating or updating/consolidating'). Formation happens either in the hot path (immediate but adds latency) or in the background after the conversation (higher recall of extracted info, no user-facing latency). Its memory manager pipeline is: take conversation + current memory state → LLM decides expand-or-consolidate → reconcile (insert/delete/consolidate) → return new state; recall ranks by similarity x importance x 'strength' (recency/frequency of use). Storage is pluggable BaseStore with hierarchical namespaces like {user_id}.

### Cognee — ECL pipeline over unified relational+vector+graph storage (2024-2026 (ongoing))
Source: https://github.com/topoteretes/cognee and https://docs.cognee.ai/core-concepts/architecture
An Extract-Cognify-Load pipeline turns raw documents into a knowledge graph: cognify chunks documents, classifies them, LLM-extracts typed entities/relationships (DataPoints defined as Pydantic models, with optional ontology grounding), generates summaries, and commits both graph edges and embeddings. Three coordinated stores: relational (documents, chunks, provenance back to source), vector (embeddings), graph (entities/relationships) — plus a session cache; API is remember/recall/forget/improve with auto-routed search strategies (graph completion, RAG completion, insights, chunks). The 'memify'/improve layer feeds rated responses back into edge weights, a production example of retrieval-feedback-driven memory tuning.

### A-MEM — Zettelkasten notes with LLM link generation and in-place memory evolution (2025-02)
Source: https://arxiv.org/abs/2502.12110 and https://github.com/agiresearch/a-mem
Each atomic note is m_i = {content c_i, timestamp t_i, LLM-generated keywords K_i, tags G_i, contextual description X_i, embedding e_i = f_enc(concat(c,K,G,X)), links L_i}. On insert, cosine top-k neighbors are retrieved and an LLM decides which links to create (L_i ← LLM(m_n ‖ M_near ‖ P_s2)) — capturing causal/conceptual connections beyond embedding similarity. Memory evolution then lets the new note rewrite each neighbor: m_j* ← LLM(m_n ‖ M_near\m_j ‖ m_j ‖ P_s3), and 'the evolved memory replaces the original' — continuous refinement but destructive, with no version history. Retrieval is plain cosine top-k (k=10) plus automatically pulling linked neighbors; it roughly doubled multi-hop F1 vs MemGPT on LoCoMo while using ~1-2.5k tokens per answer vs ~17k.

### LoCoMo benchmark — very long-term conversational memory (2024-02)
Source: https://arxiv.org/abs/2402.17753
Machine-human generated conversations grounded in personas and temporal event graphs (~300 turns, ~9k tokens, up to 35 sessions; 7,512 QA pairs) testing single-hop, multi-hop, temporal, open-domain, and adversarial (unanswerable) questions plus event summarization and multimodal dialog. Core finding: long-context LLMs and RAG both improve over naive baselines but 'still substantially lag behind human performance,' with temporal and causal reasoning the weakest areas. It became the de facto leaderboard for Mem0/Zep/MemOS/A-MEM; its known limitations (modest context length, no explicit knowledge-update scoring) pushed the field to LongMemEval.

### LongMemEval — five abilities and the winning index/retrieve/read design choices (2024-10 (ICLR 2025))
Source: https://arxiv.org/abs/2410.10813
Tests information extraction, multi-session reasoning, temporal reasoning, knowledge updates, and abstention over ~115k-token (S) to ~500-session (M) histories; commercial assistants dropped ~30% accuracy, long-context LLMs 30-60% vs oracle. The winning recipe from its unified indexing/retrieval/reading framework: (1) index at round (fine granularity) rather than session level; (2) fact-augmented key expansion — attach LLM-extracted facts/summaries as searchable keys while keeping the verbatim round as the value (+9.4% recall@k, +5.4% accuracy), because replacing raw text with extractions loses information; (3) time-aware query expansion — extract the question's time range and restrict retrieval (+11.3% recall on temporal questions); (4) reading strategy matters even with perfect retrieval (up to 10-point swing) — Chain-of-Note + JSON formatting won.

### Supermemory — SOTA LongMemEval via dual-layer timestamps and typed memory-version relations (2025-2026)
Source: https://supermemory.ai/research/longmembench/
Atomic memories are extracted from semantic chunks with ambiguous references resolved via contextual retrieval, and each carries two timestamps: documentDate (when it was said) and eventDate (when the described event actually happened). Contradiction/evolution is modeled as typed relations between memory versions: 'updates' (contradiction — favorite color Blue→Green), 'extends' (non-contradicting supplement), 'derives' (inference from multiple memories). Retrieval finds the atomic memory semantically, then injects the original source chunk for nuance — combining precision of atomic facts with fidelity of verbatim text; scores Recall@15 95% overall, 99% knowledge-update, 91% temporal vs Zep's 71.2/83.3/62.4, at ~720 mean tokens (99.4% context reduction).

### Cross-system convergence — what production systems agree on (2024-2026)
Source: Synthesis of the above (arxiv 2501.13956, 2504.19413, 2507.03724, 2502.12110, 2410.10813)
Despite different vocabularies, the systems converge on: (a) a two-layer store — an immutable raw/episodic layer plus a derived semantic layer with provenance links (Graphiti episodes→entities, Cognee chunks→graph, LongMemEval values→keys, Supermemory chunks→memories); (b) LLM-adjudicated write-time consolidation against retrieved near-neighbors rather than blind appends (Mem0's four ops, LangMem's reconcile step, A-MEM's evolution); (c) hybrid retrieval (dense + lexical + graph/link expansion + reranking); and (d) the leaders on temporal/knowledge-update tasks are exactly those that keep superseded knowledge queryable (Zep bi-temporal invalidation, Mem0^g obsolete-marking, Supermemory 'updates' relations) instead of deleting it.

### DESIGN IMPLICATIONS
- Use a two-layer data model: markdown files are the immutable episodic ground truth (Graphiti's 'episode subgraph', LongMemEval's 'values'), and a derived semantic layer (atomic facts/entities/edges) lives in a rebuildable index (e.g. SQLite with vector + FTS5 + edge tables, mirroring Cognee's relational+vector+graph triad). Every derived unit must carry provenance: file path + heading/block anchor + content hash, so the whole index can be regenerated after human edits to the vault.
- Make the atomic fact the retrieval unit but never the only stored form: LongMemEval showed extraction-only storage loses information, and Supermemory's winning pattern is 'search the atomic memory, then inject the verbatim source chunk.' Index facts as keys pointing at markdown blocks as values.
- Adopt bi-temporal timestamps on every derived fact — t_valid/t_invalid (when true in the world, cf. Supermemory's eventDate) separate from t_created/t_expired (when recorded/superseded, cf. documentDate). This is the single highest-leverage schema decision for knowledge that evolves: it enables 'what is true now', 'what was true in March', and 'what did I believe in March' as distinct queries.
- Never hard-delete on contradiction — invalidate. Set t_invalid to the superseding fact's t_valid and link the two (Zep's mechanism). Every system that scores well on knowledge-update/temporal benchmarks does soft invalidation (Zep, Mem0^g, Supermemory); base Mem0's DELETE is the anti-pattern for a personal knowledge engine where history is itself knowledge.
- Type the links between fact versions using Supermemory's minimal ontology: 'updates' (contradiction), 'extends' (compatible supplement), 'derives' (inference from multiple facts). Three relation types are enough to represent evolution and contradiction without a heavyweight ontology, and 'derives' edges give you an audit trail for machine-generated conclusions.
- The write path should be Mem0's consolidation loop: for each new candidate fact, retrieve top-k similar existing facts and have an LLM choose ADD / UPDATE / INVALIDATE(+link) / NOOP via a tool call — replacing DELETE with INVALIDATE. This prevents duplicate sprawl while preserving history.
- Run consolidation as sleep-time compute, not in the hot path: Letta's data (5x test-time compute reduction) and LangMem's background-formation tradeoff both show enrichment, linking, summarization, and contradiction-sweeps belong in an async/idle-time daemon (e.g. on file-save debounce or nightly), keeping capture instant.
- Keep a small always-loaded 'core' layer distinct from the unbounded store: profile-style, continuously rewritten documents (Letta core blocks, LangMem profiles) for stable facts — who the user is, current projects, preferences — since these need no retrieval and benefit from in-place update; use the versioned fact store for everything volatile.
- Enrich each atomic note A-MEM-style at ingest (LLM-generated keywords, tags, and a contextual description, all concatenated into the embedding) and let the LLM propose links to top-k neighbors — but unlike A-MEM's destructive in-place evolution, record neighbor updates as new versions with a version chain (MemOS MemCube's 'version chain' metadata), so evolution never silently erases prior state. In a markdown vault, wiki-links are the human-authored edge layer; LLM-proposed links should be a separate, clearly machine-attributed edge type.
- Retrieval must be hybrid: dense embeddings + BM25/FTS + one-to-two-hop link/graph expansion, fused with reciprocal-rank fusion and optionally reranked (Zep's φ_cos/φ_bm25/φ_bfs). Pure vector search is what every benchmarked system outgrew; the vault's wiki-link graph gives BFS expansion nearly for free.
- Implement time-aware query handling: parse the temporal scope of a question and filter/boost by t_valid ranges before semantic ranking (+11.3% recall on temporal questions in LongMemEval). Also index at fine granularity — heading/block level, not whole files — the round-vs-session result.
- Track usage metadata per unit (access frequency/recency, MemOS's hot/cold indicators; LangMem's importance x strength ranking) to drive ranking boosts, promotion into the core profile layer, and archival of cold facts — decay of retrieval priority, never destruction of data.
- Since the store is local-first and human-editable, treat the markdown as the source of truth that always wins: derived facts whose source anchor changed get re-extracted; human edits are effectively a privileged UPDATE/INVALIDATE stream. All derived state must be reconstructible from the vault + an append-only event log, which also keeps the design honestly local (SQLite + local embedding model suffice — no server dependency in any of the mechanisms above).

## AREA: Cognitive-science-inspired memory dynamics in AI systems (2023-2026): retrieval scoring, forgetting curves, consolidation/reflection, spaced repetition, and belief revision

### Generative Agents — recency/importance/relevance retrieval + importance-triggered reflection (Park et al., Stanford/Google) (2023-04-07 (UIST 2023))
Source: arXiv:2304.03442 (https://ar5iv.labs.arxiv.org/html/2304.03442)
Retrieval score = α_rec·recency + α_imp·importance + α_rel·relevance with all α=1, each component min-max normalized to [0,1]. Recency = 0.995^(game-hours since last retrieval); importance = LLM integer 1-10 via the exact prompt 'On the scale of 1 to 10, where 1 is purely mundane (e.g., brushing teeth...) and 10 is extremely poignant (e.g., a break up, college acceptance), rate the likely poignancy of the following piece of memory'; relevance = cosine similarity of embeddings. Reflection triggers when the sum of importance scores of events since the last reflection exceeds 150 (≈2-3 reflections/day): the agent takes the 100 most recent memories, asks for the '3 most salient high-level questions', answers them, and stores the insights as new memories with pointers to the cited source memories — reflections are themselves retrievable and can cite other reflections, building abstraction trees.

### MemoryBank — Ebbinghaus exponential forgetting with recall reinforcement (Zhong et al.) (2023-05-17)
Source: arXiv:2305.10250 (AAAI 2024)
Memory retention follows R = e^(−t/S) where t = time since last recall and S = discrete memory strength, initialized S=1 at first mention. On each recall: S ← S+1 and t ← 0, so frequently used memories decay ever slower; unrecalled memories decay toward forgetting (authors call it 'an exploratory and highly simplified memory updating model' with no explicit discard threshold). Storage is hierarchical: timestamped raw turns → daily event summaries → global summary, plus daily personality insights aggregated into a global user portrait; retrieval is dual-tower dense (DPR-style) over FAISS.

### Sleep-time compute — offline context re-representation during idle time (Letta / UC Berkeley, Lin et al.) (2025-04-17)
Source: arXiv:2504.13171 (https://arxiv.org/html/2504.13171v1; code: github.com/letta-ai/sleep-time-compute)
During idle periods a 'sleep agent' transforms raw context c into learned context c′ = S(c) by inferring likely future questions and pre-computing reasoning, via two tool calls: rethink_memory (rewrites the memory block with new inferences, up to 10 iterations) and finish_rethinking. At test time the main agent answers from c′, cutting test-time compute ~5x at equal accuracy on Stateful GSM-Symbolic/AIME, raising accuracy up to 13-18% when sleep-time compute is scaled, and amortizing to 2.5x lower cost/query at 10 queries per shared context. Critical caveat: gains grow with query predictability from context; for unpredictable queries plain test-time scaling wins — so consolidate only contexts you expect to be queried.

### FSRS (Free Spaced Repetition Scheduler) — power-law forgetting with three-component memory model (Jarrett Ye / open-spaced-repetition) (FSRS-4.5: 2023; FSRS-6: 2025)
Source: https://github.com/open-spaced-repetition/awesome-fsrs/wiki/The-Algorithm
Models each item as (Difficulty D∈[1,10], Stability S in days, Retrievability R). Forgetting curve (FSRS-4.5/5/6): R(t,S) = (1 + FACTOR·t/S)^DECAY with FACTOR=19/81, DECAY=−0.5, so R(S,S)=0.9 — a power law with a fatter tail than exponential, empirically better-fitting human forgetting. Next interval for target retention r: I(r,S) = (S/FACTOR)·(r^(1/DECAY) − 1). On successful review, stability grows by S′ = S·(1 + e^(w8)·(11−D)·S^(−w9)·(e^(w10·(1−R))−1)·hardPenalty(w15)·easyBonus(w16)) — i.e., growth is larger for easier items, shows diminishing returns in S (S^(−w9)), and is larger the closer the item was to being forgotten (spacing effect via e^(w10(1−R))). On lapse: S′_f = w11·D^(−w12)·((S+1)^(w13)−1)·e^(w14·(1−R)). Difficulty updates with mean reversion D′ = w7·D0(3) + (1−w7)·(D − w6·(G−3)) to prevent 'ease hell'. ~17-21 parameters fitted per user by gradient descent on review logs; used as Anki's default scheduler.

### SuperMemo SM-2 + incremental reading — easiness factors and priority queues for PKM (SM-2: 1987; priority queue: SuperMemo 13, 2006)
Source: https://super-memory.com/english/ol/sm2.htm and https://help.supermemo.org/wiki/Priority_queue
SM-2: each item has easiness factor EF∈[1.1, 2.5] (init 2.5), updated after review quality q∈0-5 by EF′ = EF + (0.1 − (5−q)·(0.08 + (5−q)·0.02)); intervals I(1)=1, I(2)=6, I(n)=I(n−1)·EF, reset on failure. Incremental reading turns reading into a 'funnel of knowledge': articles → extracts → cloze deletions, all scheduled in one priority queue where every element carries a user-set priority; auto-sort and auto-postpone let overload degrade gracefully — low-priority material silently slips while high-priority material keeps its schedule. Articles carry an A-Factor governing how fast review intervals grow (A-Factor 2 ⇒ intervals double).

### MEM1 — RL-trained constant-memory consolidation into a shared internal state (Zhou et al., MIT/NUS) (2025-06-18)
Source: arXiv:2506.15841
End-to-end RL framework where at every turn the agent overwrites a single compact internal state <IS> that jointly serves as memory and reasoning scratchpad: it integrates prior state with new observations and strategically discards redundant/irrelevant content, keeping context size constant over arbitrarily long horizons. Trained with task-outcome RL (no supervision on what to keep), MEM1-7B gets 3.5x better performance with 3.7x less memory than Qwen2.5-14B on 16-objective multi-hop QA and generalizes beyond training horizon. Demonstrates that 'what to remember' can be learned from task reward alone rather than hand-coded.

### RMM (Reflective Memory Management) — prospective topic consolidation + retrospective citation-rewarded retrieval (Tan et al., Google/UIUC, ACL 2025) (2025-03-11)
Source: arXiv:2503.08026
Prospective Reflection (at session end): an LLM decomposes the session into topic-based memories (topic summary + raw dialogue segment); for each, retrieve Top-K similar bank entries and an LLM decides ADD (new topic) vs MERGE (update of an existing topic) — consolidation at write time, organized around semantic topics rather than fixed session/turn boundaries. Retrospective Reflection (online, every response): retriever fetches Top-K=20, a lightweight reranker picks Top-M=5 via residual adaptation q′=q+W_q·q, m′_i=m_i+W_m·m_i, scores s_i=q′ᵀm′_i with Gumbel noise g_i=−log(−log(u_i)) and softmax(s̃_i/τ) sampling; the generator LLM emits citations with its answer, each retrieved memory gets reward +1 if cited / −1 if not, and the reranker is updated by REINFORCE: Δφ = η·(R−b)·∇_φ log P(M_M|q,M_K;φ). >10% accuracy gain on LongMemEval over no-memory-management baselines.

### Mem0 / Mem0g — LLM-arbitrated ADD/UPDATE/DELETE/NOOP conflict resolution (Chhikara et al.) (2025-04-28)
Source: arXiv:2504.19413
Two-phase pipeline: extraction (LLM distills candidate facts from the latest exchange using conversation summary + recent context) then update: for each candidate fact, retrieve top-s semantically similar existing memories and have the LLM choose ADD (novel), UPDATE (augment/refine existing), DELETE (new info contradicts stored memory), or NOOP — making contradiction handling an explicit classification step at write time. Mem0g adds a graph variant: entities as nodes, relations as edges; new triplets are embedding-matched against existing nodes, and a conflict-detection mechanism finds contradicting relationships, marking obsolete edges invalid rather than removing them. Reports SOTA-competitive LoCoMo accuracy at a fraction of full-context latency/tokens.

### Zep / Graphiti — bi-temporal knowledge graph with edge invalidation instead of deletion (2025-01)
Source: https://github.com/getzep/graphiti (paper: arXiv:2501.13956)
Every relationship edge carries four timestamps: created_at (ingestion), valid_at (when the fact became true in the world), invalid_at (when superseded), expired_at (system-side versioning). On contradiction the old edge's validity window is closed and a new edge opened — e.g., plan change Starter→Enterprise invalidates the Starter edge rather than overwriting it — preserving a queryable history of how state evolved and guaranteeing the agent never faces stale-vs-current ambiguity at retrieval. Contradiction detection runs at ingestion by comparing new edges against semantically related existing edges with an LLM. This is the cleanest production implementation of belief revision as temporal supersession.

### A-MEM — Zettelkasten-style agentic memory with LLM-driven memory evolution (Xu et al., Rutgers) (2025-02-17 (NeurIPS 2025))
Source: arXiv:2502.12110 (https://arxiv.org/html/2502.12110v1)
Each note m_i = {content c_i, timestamp t_i, LLM-generated keywords K_i, tags G_i, contextual description X_i, embedding e_i = f_enc[concat(c_i,K_i,G_i,X_i)], links L_i}. On insert: retrieve top-k neighbors by cosine similarity s_n,j = (e_n·e_j)/(|e_n||e_j|); an LLM decides which links to establish (L_i ← LLM(m_n ∥ M_near ∥ P_s2)). Memory evolution: for each neighbor m_j, the LLM may rewrite it — m_j* ← LLM(m_n ∥ M_near\m_j ∥ m_j ∥ P_s3) updating its context/keywords/tags — so old notes are continuously reinterpreted in light of new experience rather than frozen at write time.

### MemoryOS — OS-style hierarchical memory with heat-based promotion/eviction (Kang et al., BUPT/Tencent, EMNLP 2025 oral) (2025-05-30)
Source: arXiv:2506.06326 (https://arxiv.org/html/2506.06326)
Three tiers: STM = FIFO queue of 7 dialogue pages with chain metadata; overflow pages move to mid-term memory where they are grouped into topic segments by F_score = cos(e_s,e_p) + Jaccard(K_s,K_p) with join threshold θ=0.6. Each segment has Heat = α·N_visit + β·L_interaction + γ·R_recency with α=β=γ=1 and R_recency = exp(−Δt/μ), μ=1e7 s (~116 days); segments with Heat > τ=5 promote their content into long-term personal memory (90-dimension user traits, user KB and agent traits as fixed-size 100-entry FIFO queues), while lowest-heat segments are evicted when capacity is exceeded. +49.11% F1 over baselines on LoCoMo with GPT-4o-mini.

### HippoRAG — hippocampal memory indexing theory via Personalized PageRank (Gutiérrez et al., OSU/Stanford, NeurIPS 2024) (2024-05-23)
Source: arXiv:2405.14831 (follow-up HippoRAG 2: arXiv:2502.14802)
Maps human long-term memory onto RAG: LLM = neocortex (extracts triples into an open KG at indexing = pattern separation), retrieval encoder = parahippocampal region (links query entities to graph nodes), and Personalized PageRank over the KG = hippocampal pattern completion (spreading activation from query-entity seed nodes retrieves whole multi-hop contexts in one cheap graph pass, no iterative retrieval). Node probabilities are aggregated back to passages for ranking. Outperforms iterative-retrieval SOTA on multi-hop QA at 10-30x lower cost; HippoRAG 2 (2025-02) extends it to continual-learning-style memory over passages.

### Memory-R1 — RL-learned memory operations replacing heuristics (Yan et al.) (2025-08-27)
Source: arXiv:2508.19828
Two agents fine-tuned with outcome-driven RL (PPO/GRPO): a Memory Manager that learns when to ADD/UPDATE/DELETE/NOOP on an external memory bank, and an Answer Agent that filters retrieved candidates ('memory distillation') before reasoning. With only 152 training QA pairs it beats strong heuristic pipelines (including Mem0-style) across LoCoMo, MSC, and LongMemEval at 3B-14B scales. Evidence that the store/update/forget policy itself is learnable from downstream task reward, with very little supervision.

### LightMem — Atkinson-Shiffrin three-stage memory with sleep-time LTM updates (Zhang et al.) (2025-10)
Source: arXiv:2510.18866 (https://openreview.net/forum?id=dyJ0GWpjJB)
Maps the classic sensory→short-term→long-term human memory pipeline onto LLM memory: Light1 (sensory) does lightweight compression/filtering of raw input and topic grouping; Light2 (STM) consolidates topic groups into organized summaries; Light3 (LTM) applies 'sleep-time updates' — deferring expensive long-term consolidation to offline phases, run in parallel, decoupling inference from consolidation. Large token/latency savings versus heavyweight memory systems while preserving accuracy — the key claim is that most memory maintenance should not happen on the critical path of a user turn.

### STALE — benchmark: agents fail to notice their memories are no longer valid (2026-05)
Source: arXiv:2605.06527 (https://arxiv.org/html/2605.06527v1)
Benchmark for temporal memory invalidation: conflicts are often implicit — e.g., user said they live in Seattle, later mentions setting up utilities for a new Portland apartment — requiring belief revision with no surface contradiction. Shows current retrieval-based memory systems largely cannot detect such invalidations (retrieval scores stale and fresh facts alike); measures whether agents revise stored beliefs when new evidence arrives rather than merely retrieving static facts. Related 2026 work (CUPMem) treats each new observation as a potential state update, deciding pre-query whether older memories remain usable, need revision, or must be blocked.

### TOKI — bitemporal operator algebra for contradiction resolution in persistent agent memory (2026-06)
Source: arXiv:2606.06240
Formalizes agent memory writes as operators over a bitemporal store: every belief update carries valid time, system (transaction) time, and provenance, and contradiction resolution becomes a deterministic algebra over these annotations rather than ad-hoc LLM judgment. Kin to AGM belief revision applied to agent memory: supersession edges create new revisions with formal guarantees (success, consistency, minimal change). Complementary 2026 finding ('Don't Ask the LLM to Track Freshness', arXiv:2606.01435): a deterministic recipe — newest valid-time wins, ties broken by provenance reliability — beats prompting the LLM to reason about which fact is fresher.

### Language Models Need Sleep — parametric consolidation: distillation 'sleep' + RL 'dreaming' (2026-06)
Source: arXiv:2606.03979
Proposes a sleep phase that converts fragile in-context/short-term memories into weights: memory consolidation via upward distillation (on-policy distillation + RL-based imitation learning seeds a larger network with the smaller/session model's memories), and a dreaming phase where the model generates synthetic rehearsal data via RL to consolidate new knowledge without human supervision. Reported to help on long-horizon continual learning, knowledge incorporation, and few-shot generalization. Represents the 2026 shift from prompt-level consolidation (rewriting text memories) toward parameter-level consolidation, directly mirroring hippocampal-to-neocortical systems consolidation during sleep.

### Ebbinghaus-curve LLM memory management framework (ICICT 2026) (2026)
Source: https://dl.acm.org/doi/full/10.1145/3803291.3803294
A 2026 cognitive-science-driven design paper applying the Ebbinghaus forgetting curve to long-context management in LLMs — evidence that exponential-decay retention scoring (MemoryBank lineage) is still the standard template for decay-based memory pruning in current literature, with the main open questions being strength-update rules and consolidation scheduling rather than the curve shape itself.

### DESIGN IMPLICATIONS
- Retrieval scoring (use as default): score(m,q) = w_rel·norm(cos(e_q,e_m)) + w_rec·norm(0.995^h) + w_imp·norm(imp/10), where h = hours since m was last ACCESSED (not created), imp = LLM 1-10 'poignancy' rating assigned once at write time (Park et al.'s exact prompt works verbatim), and norm = min-max over the candidate set. Equal weights are a proven starting point; store last_accessed_at and bump it on every retrieval so recency is reinforcement-sensitive.
- Decay: prefer FSRS's power law over MemoryBank's exponential. Per memory keep Stability S (days) and compute retrievability R(t,S) = (1 + (19/81)·t/S)^(−0.5), so R(S,S)=0.9 and S is interpretable as 'days until 90% retrievability'. Power-law tails mean old-but-stable memories never crash to zero, which matches human forgetting better than e^(−t/S). Use R directly as the recency/decay term in retrieval scoring if you want one unified signal.
- Reinforcement: reinforce only on USE, not on retrieval — RMM's key signal is whether the generator actually cited the memory in its answer (+1 cited / −1 retrieved-but-unused). On a positive use event update S′ = S·(1 + e^a·(11−D)·S^(−b)·(e^(c·(1−R))−1)) (FSRS form: biggest boost when the memory was nearly forgotten — the spacing effect — and diminishing returns once S is large; a,b,c ≈ FSRS defaults w8,w9,w10). Minimal viable fallback: MemoryBank's S ← S+1, t ← 0. The −1 signal can feed a lightweight reranker later (REINFORCE: Δφ = η·(R−b)·∇_φ log P), but logging citations is valuable even before any learning.
- Importance drift: give each memory a difficulty/importance value with mean reversion, D′ = k·D_default + (1−k)·(D ± δ), so repeated small signals can't drive runaway importance inflation (FSRS's 'ease hell' fix). Re-rate importance during consolidation, not on the hot path.
- Never hard-delete facts — supersede them. Use Zep/Graphiti's bi-temporal scheme on every factual assertion: created_at, valid_at, invalid_at, expired_at. On contradiction, close the old fact's validity window and open a new fact; queries default to currently-valid facts but history stays queryable ('where did I work in 2024?'). Reserve actual eviction for low-value episodic clutter, via capacity-triggered lowest-heat eviction (MemoryOS), and archive rather than destroy when R drops below ~0.1.
- Contradiction handling at write time (Mem0 pipeline): for each extracted candidate fact, retrieve top-s similar existing memories and classify ADD / UPDATE / SUPERSEDE(=DELETE) / NOOP with the LLM. But per 2026 results, don't ask the LLM to decide freshness: resolve which fact wins deterministically (newest valid_at wins; ties broken by source reliability/provenance) and only use the LLM to detect that two facts concern the same slot. When evidence genuinely conflicts (equal recency, both plausible), store an explicit BOTH/contested state instead of silently picking a winner — STALE shows implicit invalidation (Seattle→'new apartment in Portland') is the failure mode to test for.
- Consolidation cadence — run three distinct loops: (1) Session-end prospective reflection (RMM): decompose the session into topic-scoped memories (topic summary + raw source), retrieve Top-K similar bank entries per topic, LLM decides merge-vs-add. Topics, not sessions, are the right unit of consolidation. (2) Importance-triggered reflection (Generative Agents): accumulate importance of new memories; when the running sum exceeds ~150 (on the 1-10 scale, ≈ every 20-40 notable events), take the ~100 most recent memories, generate the 3 most salient questions, answer them, and store insights WITH citation links to source memories — insights then compound (reflections over reflections). (3) Idle-time sleep compute (Letta): a bounded rethink loop (≤10 rewrite iterations) that rewrites a 'learned context' summary block per active project/person/topic, pre-answering predictable questions; only run it for contexts likely to be queried again — it amortizes ~2.5x at ~10 queries/context and is wasted on unpredictable ones.
- Memory evolution on insert (A-MEM): when writing a new note, retrieve top-k neighbors, let the LLM (a) decide explicit links and (b) optionally rewrite neighbors' contextual description/tags in light of the new note. This is the cheapest form of knowledge evolution — old notes get reinterpreted without a global reindex — and it's a natural extra step inside the idle-time loop.
- Tiered storage with promotion by engagement heat (MemoryOS): STM = raw recent chunks in a small FIFO (≈7); MTM = topic segments grouped by F = cos(e_seg,e_page) + Jaccard(keywords) with join threshold ≈0.6, each carrying Heat = N_visits + interaction_length + e^(−Δt/μ) (μ ≈ 10^7 s); Heat > τ promotes distilled content into the durable user/knowledge profile; capacity overflow evicts lowest-heat segments. This gives you working-memory vs consolidated-knowledge separation with two tunable dials (θ, τ). Keep all LTM/profile updates off the interactive path (LightMem's core lesson).
- Multi-hop retrieval without iterative search (HippoRAG): maintain a lightweight entity/concept graph over notes (triples extracted at write time); at query time, extract query entities and run Personalized PageRank seeded on their nodes, aggregating node scores back to notes. One graph pass replaces multi-step retrieval chains and complements vector similarity — vector search finds 'about the same thing', PPR finds 'connected to the same things'.
- Human-facing resurfacing: schedule note/flashcard resurfacing with FSRS at target retention r=0.9: next_interval I = (S/(19/81))·(r^(−2) − 1) ≈ S when r=0.9; per-item parameters can be fitted from the user's review log (open-source FSRS optimizers exist). Wrap it in SuperMemo's incremental-reading discipline: everything (documents, extracts, clozes, stale memories needing reconfirmation) lives in ONE priority queue with auto-postpone, so overload sheds low-priority items gracefully instead of collapsing the schedule. Also surface 'this fact may be stale — still true?' prompts when a high-importance fact's R decays below threshold: user confirmation is a recall event (reinforce), correction is a supersession event.
- Learned vs heuristic policies: MEM1 and Memory-R1 show add/update/delete policies are learnable from task reward with tiny data (152 QA pairs), and 2026 work is moving consolidation into weights ('sleep'/'dreaming' via distillation + RL). For a local-first engine, ship the heuristic formulas above first — they capture most of the value — but log every (memory, operation, citation, outcome) tuple from day one so a learned manager/reranker can be trained later without a data cold-start.
- Architecture framing: classify every memory operation as write-time (extract facts, rate importance, detect conflicts, link neighbors), read-time (score = relevance + retrievability + importance, rerank, PPR), or idle-time (topic merge, reflection/insights, learned-context rewriting, profile promotion, decay sweeps, re-rating). The consistent lesson across sleep-time compute, LightMem, RMM, and MemoryOS: keep read-time trivial and push everything expensive to idle time — that is what 'sleep' buys you, and on local-first hardware (limited compute, but 100% idle-time availability) it is the single highest-leverage design decision.

## AREA: AI-powered personal knowledge management: product landscape 2025-2026 (agent-built wikis, Obsidian AI plugins, local-first PKM, MCP memory servers, commercial tools)

### obsidian-wiki (Ar9av) — the comparison target (2025-2026, active; 3.1k stars)
Source: https://github.com/Ar9av/obsidian-wiki
A framework of 39 markdown-prompt 'skills' (no runtime code for the skills themselves) that any coding agent (Claude Code, Cursor, Codex, Windsurf, Gemini CLI, 12+ others via a symlinked .skills/ directory) reads and executes to build an Obsidian vault: slash commands for ingest (/wiki-ingest, /wiki-capture, /wiki-update, per-agent history miners), query (/wiki-query with [[wikilink]] citations, /wiki-narrate, /wiki-digest, /wiki-context-pack), and maintenance (/wiki-lint, /wiki-dedup, /cross-linker, tag-taxonomy, wiki-synthesize). Vault convention: category dirs (concepts/entities/skills/references/synthesis/journal/projects), index.md, log.md, hot.md (~500-word semantic snapshot), _raw/ staging, _staging/ review queue, and a .manifest.json ingest ledger enabling delta-only re-processing; every page carries mandatory frontmatter (title/category/tags/sources/created/updated/summary/provenance) with claims tagged extracted/inferred/ambiguous. Graph export via wiki-export to graph.json, GraphML, Neo4j Cypher, self-contained graph.html, and a lossless 'OKF v0.1' bundle, with wiki-import for round-trips.

### obsidian-wiki — limitations (from docs + issue tracker) (2026)
Source: https://github.com/Ar9av/obsidian-wiki/issues?q=is%3Aissue
Everything is pull-based: capture, staging promotion, sync, and lint all require manual slash-command invocation (only optional cron for git sync). Retrieval defaults to grep/glob; semantic search is delegated to an optional external tool (QMD) with two manually configured collections that silently no-op if unset. The issue tracker shows the core fragility of prompt-defined systems: manifest schema divergence between SKILL.md instructions and the Python cache.py (#134/#135/#136), missing files in published wheels (#143, #152), fragmented git-sync implementations (#153), and no migration path when conventions change (#146 trust-ledger rollout broke legacy vaults). The maintainer's own roadmap admits weak cross-referencing, imperfect dedup, and poor large-vault support; graph edges are untyped wikilinks, and there is no temporal model, decay, or proactive surfacing.

### Smart Connections (Obsidian plugin, brianpetro) (active 2025-2026)
Source: https://github.com/brianpetro/obsidian-smart-connections
Local-first semantic similarity for Obsidian: embeds notes/blocks on-device with a bundled small model (TaylorAI/bge-micro-v2, 384-dim; ~3MB per 1,000 notes), zero API key, then shows a note-first 'Connections' pane of related notes and a question-first 'Smart Lookup', plus optional cloud-LLM Smart Chat. Data model is embeddings-over-existing-markdown — it never writes or restructures knowledge, only surfaces similarity. User complaints (issue #999 'total mess', forum threads on 'stopped working'/stuck indexing, 0% embedding coverage) center on reliability of the indexing pipeline and breakage across versions; it also has no claim-level structure, no graph semantics, and no synthesis.

### Obsidian Copilot (logancyang) (active 2025-2026)
Source: https://github.com/logancyang/obsidian-copilot
Chat + Vault QA over an Obsidian vault using a local vector store with cited sources, multi-model support (GPT-5.1, Gemini, Claude), and a paid 'Plus/agent' tier whose backend is closed-source and proprietary. Practical scale ceiling acknowledged by the maintainer: ~1GB vault fine, ~10GB is the limit of the semantic-search route (discussion #1959), with an index-free fallback. Recurring issues include embedding-model indexing errors, vault-access failures (#1567, #655), and a wrong Vault-QA pre-prompt that made the model rephrase instead of answer (#1198) — again showing prompt-layer fragility; it reads the vault but does not build or maintain knowledge.

### Khoj (khoj-ai) (active 2025-2026)
Source: https://github.com/khoj-ai/khoj
Self-hostable 'AI second brain': RAG over markdown/org/PDF/GitHub/Notion sources, semantic search, custom agents with personas/tools, scheduled automations, deep research, and clients for Obsidian, Emacs, web, WhatsApp; works with any local or online LLM and exposes REST + MCP. Data model is index-over-your-files (Postgres + embeddings) rather than a curated graph — it retrieves, it doesn't compile knowledge or track provenance/contradictions. Self-hosting friction is the loudest complaint stream: Docker auth/env issues (#959, #1100 local Ollama connection failures), hardcoded cloud service assumptions (#1259 Firecrawl), and setup complexity, plus the operational weight of running a Django/Postgres server for personal use.

### Reor (reorproject) — cautionary tale (archived 2026-03-07)
Source: https://github.com/reorproject/reor
Desktop 'private & local AI PKM' (Electron; Ollama + Transformers.js + LanceDB) that chunked markdown notes into a local vector DB, auto-linked related notes, and did local RAG Q&A. Despite 8.6k stars it was archived March 2026 with 113 open issues — evidence that a standalone local-AI note app is hard to sustain, and that auto-similarity-linking alone wasn't enough of a product. Its data model (markdown files + derived embedding index) survives its death precisely because it was plain files, reinforcing the plain-text-substrate lesson.

### Anytype (active 2025-2026)
Source: https://blog.anytype.io/february-community-update-2026/
Local-first, CRDT-synced object system: everything is a typed Object with user-defined Types and Relations (typed properties/links), organized in Sets/Collections — the richest end-user data model in the local-first space, essentially a personal graph database. AI is late and cautious: their stated principle is user choice among no/local/cloud AI, arguing their typed object graph is unusually well-suited to machine reasoning, but as of early 2026 AI features are nascent — so the best structured local-first data model has the weakest AI, the inverse of the Obsidian plugin world. Known weaknesses: steep learning curve, weaker ecosystem/API than Obsidian, team-editing polish.

### Basic Memory (basicmachines-co) (active 2025-2026; 3.6k stars)
Source: https://github.com/basicmachines-co/basic-memory
MCP server that gives LLMs a persistent knowledge base as plain Markdown: entities are files whose body encodes categorized Observations ('- [method] fact #tag') and typed Relations ('- pairs_well_with [[X]]'), indexed into SQLite with hybrid FTS + FastEmbed vector search, optional cross-encoder reranking, and graph traversal via memory:// URLs; tools carry MCP behavior hints for progressive discovery. It is the closest existing thing to an 'agent-maintained typed knowledge graph in markdown'. Gaps: no automatic capture (the agent must be told to write), no consolidation/decay/temporal reasoning, sync across devices is DIY (git/Syncthing), local install needs Python/uv, and the cloud tier ($15/mo) is the answer to mobile — AGPL-3.0 licensed.

### mcp-memory-service (doobidoo) (active 2025-2026)
Source: https://github.com/doobidoo/mcp-memory-service
Persistent memory MCP server for Claude and agent frameworks (LangGraph, CrewAI, AutoGen) with semantic search over multiple backends (SQLite-vec + ONNX embeddings, sentence-transformers, ChromaDB) and a REST API + knowledge graph. Its distinctive mechanism is 'dream-inspired' autonomous consolidation: background jobs cluster, compress, and decay memories over time — one of the only projects implementing a memory lifecycle rather than append-only storage. Weaknesses: memories are opaque stored blobs rather than human-readable/ownable files, the deployment matrix (backends x transports x OAuth) is complex, and consolidation quality is heuristic rather than curated.

### Anthropic reference memory MCP server (maintained reference implementation)
Source: https://github.com/modelcontextprotocol/servers/tree/main/src/memory
The canonical minimal design: a knowledge graph of Entities (name, type, observations list), directed active-voice Relations, and atomic one-fact Observations, persisted as a single memory.jsonl file, with 9 tools (create/delete entities-relations-observations, read_graph, search_nodes, open_nodes). Search is naive substring matching over names/types/observations; read_graph returns the entire graph — neither scales beyond toy size, and error handling silently ignores missing/duplicate items. Its value to a builder is the schema vocabulary (entity/relation/observation) it standardized, which Basic Memory and others elaborated; it demonstrates the floor, not the ceiling.

### claude-mem (Claude Code memory plugin) (2025-2026)
Source: https://betterstack.com/community/guides/ai/claude-mem/
Claude Code plugin that hooks all five lifecycle events to automatically capture session activity, compress it ~10x via the Agent SDK into searchable observations (SQLite), and inject relevant compressed context at SessionStart; 'Endless Mode' compresses tool outputs into ~500-token observations in real time to extend sessions. It proves hook-driven ambient capture works — no manual /capture command — which is exactly what obsidian-wiki lacks. Limitations reviewers flag: lossy compression whose quality depends on the summarizer model, no multi-machine sync, tuning required (injection amount, compression aggressiveness), and scope confined to coding sessions rather than general knowledge.

### Cognee + Cognee MCP (active 2025-2026; 500x pipeline growth in 2025)
Source: https://github.com/topoteretes/cognee
Open-source 'AI memory engine' running an ECL pipeline (Extract, Cognify, Load): classify documents, chunk, LLM-extract entities/relations, summarize, embed into a vector store and commit typed edges to a graph DB; the MCP server exposes ~14 tools for agents to read/write/reason over the graph. Its 'memify' post-processing is the most advanced graph-lifecycle mechanism in the landscape: prunes stale nodes, strengthens frequently used connections, reweights edges from usage signals, and adds derived facts. Costs of that power: heavy machinery (LLM calls per ingest, graph + vector infra) that its own docs call overkill for personal-preference memory, latency unsuitable under ~200ms, and quality that materially depends on custom ontology work for specific domains.

### Mem.ai / Mem 2.0 (Mem 2.0 released early 2026)
Source: https://www.producthunt.com/products/mem-2-0/reviews
Commercial 'self-organizing' notes: dump notes, meeting transcripts, and PDFs and the AI auto-connects and surfaces related material with no folders/tags; Mem Chat answers from your corpus with source attribution. Mem 2.0 was an engine rewrite responding to years of performance/sync complaints — now faster, but reviews still flag weak exact-keyword search (a warning that pure-semantic retrieval frustrates users), restrictive free limits (25 chats/25 PDF pages per month), limited third-party integrations, and a proprietary cloud data model with no local ownership. Validates auto-organization as a paid value prop while demonstrating the trust cost of opaque storage.

### Tana (active 2025-2026)
Source: https://www.saner.ai/blogs/tana-reviews
Cloud outliner + database where 'supertags' apply user-defined schemas (fields, types, references) to any node, making structure queryable; by 2026 it added agentic AI — meeting agents transcribing in 60 languages and agents generating PRs/specs/prototypes from graph context, multi-model (GPT-5.1, Gemini 3 Pro, Claude). Complaints: one of the steepest learning curves in the category (days-to-weeks), performance lag at tens of thousands of nodes, weak/unreliable offline editing (online-first), underpowered mobile, and non-rollover AI credits creating recurring costs. Tana proves demand for typed personal schemas + agents, and that cloud-first + manual schema-authoring are its soft spots.

### Rewind → Limitless → Meta (lifelogging endgame) (acquired by Meta 2025-12-05)
Source: https://www.techtimes.com/articles/314655/20260216/best-ai-notetaking-devices-2026-comparing-rewind-pendant-plaud-ai-recorder-other-wearable-mics.htm
Rewind (screen/audio capture on Mac) pivoted into Limitless, a wearable pendant continuously recording and transcribing conversations with Consent Mode and 'Confidential Cloud', pursuing zero-friction ambient capture with search/summarize-later. Meta acquired Limitless in December 2025; pendant sales stopped and support runs only through 2026 — users who built life archives on it face a dead end, triggering refund demands. The arc demonstrates both that ambient capture is the frontier users want and that trusting a venture-backed cloud with a personal memory corpus is structurally risky.

### The 'write-only second brain' problem (user sentiment) (2025-2026)
Source: https://dessence.ai/blog/why-second-brains-keep-becoming-graveyards
A 2025 'I deleted my second brain' HN thread (1,200+ comments) converged on the diagnosis that most PKM systems are write-only: capture succeeds, retrieval and reuse fail, because maintenance cost outlasts reward and recall requires remembering your own filing logic months later. The personal knowledge-base AI market reached ~$1.65B in 2025 (30%+ CAGR) even as most vaults rot — the gap between capture tooling and knowledge that actually resurfaces at the moment of need is the central unmet demand every product above only partially addresses.

### DESIGN IMPLICATIONS
- Ambient capture, not slash commands: obsidian-wiki's biggest structural weakness is that every operation (/wiki-capture, staging promotion, lint, sync) is manually invoked; claude-mem proves lifecycle-hook-driven automatic capture works. An advanced engine should observe (session hooks, file watchers, MCP tool-call taps) and compile continuously, with the human reviewing rather than initiating.
- Put invariants in code, prompts only orchestrate: obsidian-wiki's issue tracker is dominated by drift between SKILL.md prose and Python code (manifest schema mismatches #134/#135/#136, broken wheels, no migrations). Define the vault schema, manifest, and graph operations as a typed, versioned library with validation and migrations; let LLM prompts call it, never re-specify it.
- Typed knowledge graph over untyped wikilinks: obsidian-wiki's graph is bare [[wikilinks]]; the MCP memory lineage (Anthropic reference → Basic Memory → Cognee) shows entities + typed relations + atomic observations enable traversal, contradiction detection, and reasoning. Adopt entity/relation/observation with types, but keep the Basic Memory trick of encoding it in human-readable markdown so files stay the source of truth.
- Memory lifecycle is the open niche: almost nobody ships temporal reasoning — only mcp-memory-service (dream-inspired decay/clustering) and Cognee's memify (prune/reinforce/derive) attempt it, both outside the PKM file world. Build first-class time: validity intervals on claims, supersession when contradictions arrive, reinforcement from retrieval hits, decay/archival of stale knowledge — this is the clearest differentiation from obsidian-wiki's static pages.
- Retrieval must be hybrid, local, and zero-config: obsidian-wiki defaults to grep with semantic search as an optional external dependency (QMD) that silently no-ops; Mem users complain pure-semantic search loses exact keywords; Copilot caps at ~1GB vaults. Ship embedded hybrid retrieval (SQLite FTS + small local embedding model like bge-micro/FastEmbed + graph-neighborhood expansion + optional reranking) inside the tool, with incremental indexing designed for 100k+ pages from day one.
- Solve the write-only graveyard with proactive surfacing: the dominant user complaint across the landscape is capture-without-resurfacing. Add push channels — context injection at session start (claude-mem), 'related to what you're doing now' panes (Smart Connections), scheduled digests, and stale/contradicted-knowledge alerts — so the engine spends knowledge, not just stores it.
- Keep and extend obsidian-wiki's provenance model — it's its best idea: extracted/inferred/ambiguous claim tagging, source-attributable frontmatter, and staged writes with human review are genuinely ahead of everyone; users distrust AI-written notes. Extend to per-claim confidence scores, retrieval-time provenance display, and a trust ledger enforced by code (obsidian-wiki's trust rollout broke old vaults because it wasn't versioned).
- Plain files + lossless export as survival insurance: Reor archived, Limitless swallowed by Meta, Mem is an opaque cloud — while markdown vaults outlive their tools. Store canon as plain markdown, treat SQLite/vector/graph stores as disposable derived indexes, and support lossless round-trip export (obsidian-wiki's OKF bundle + GraphML/Neo4j export is the right instinct; make round-trips lossless everywhere, not just OKF).
- Expose the engine as an MCP server, not per-agent skill folders: obsidian-wiki symlinks .skills/ into 12+ agent directories — brittle and duplicative (dangling-symlink issues filed). A single MCP server with behavior-hinted tools (Basic Memory's pattern) serves Claude Code, Cursor, Desktop, and future agents from one interface, while slash commands become thin wrappers.
- Emergent schema with progressive typing: Tana shows typed personal schemas (supertags) are powerful but its manual authoring creates a brutal learning curve; obsidian-wiki lets schema 'emerge organically' with no typing at all; Cognee finds custom ontologies materially improve quality. Middle path: infer entity types and relation vocabularies from accumulated content, propose them for confirmation, then enforce them — schema as a byproduct of use.
- Tiered compute economics: Cognee-style LLM-per-ingest pipelines are too heavy and slow for personal use, and Tana's non-rollover AI credits annoy users. Reserve LLM calls for compilation/synthesis (batched, async), run retrieval and linking on local embeddings and the graph index (fast, free), and make every LLM-dependent stage degrade gracefully — the QMD 'graceful degradation' pattern done properly.
- Synthesis is where to leapfrog: dedup, cross-linking, and contradiction flagging are now table stakes (obsidian-wiki has all three, imperfectly). The unclaimed layer is genuine synthesis — periodic jobs that detect cross-domain connections, fill gaps (wiki-synthesize is embryonic), generate derived claims with 'inferred' provenance, and measure knowledge-graph health over time — turning the vault from an archive into a compounding asset.
- Plan for sync and mobile capture early: claude-mem has no multi-machine story, Basic Memory punts to git/Syncthing, Tana fails offline, Anytype nails CRDT sync but lacks AI. Git-based sync of the markdown canon (with derived indexes rebuilt locally per device) plus a lightweight mobile capture inbox covers the gap without building a sync service.

## AREA: LLM memory and personal knowledge systems — frontier survey, mid-2025 through mid-2026

### Zep / Graphiti — bitemporal knowledge-graph memory (2025-01)
Source: https://arxiv.org/abs/2501.13956
Zep's Graphiti engine stores agent memory as a temporally-aware knowledge graph where every edge carries bitemporal annotation: event time (when the fact was true in the world) and ingestion time (when the system learned it). Contradictory new facts don't delete old ones — they invalidate them with a validity interval, so 'what was true in Q1?' is answerable. It beat MemGPT on Deep Memory Retrieval and remains the reference design for temporal fact memory; the 2026 graph-memory taxonomy (arXiv 2602.05665) still treats it as a core system.

### A-MEM — Zettelkasten-style agentic memory (NeurIPS 2025) (2025-02)
Source: https://arxiv.org/abs/2502.12110
Each new memory becomes a structured note (contextual description, keywords, tags); the system then agentically generates links to related historical notes, and — its key mechanism — new memories trigger 'memory evolution': updates to the attributes and contextual text of existing notes. This makes the store a living network rather than an append-only log, directly validating the interlinked-notes model for agent memory.

### Sleep-time compute (Letta) — offline thinking between interactions (2025-04-17)
Source: https://arxiv.org/abs/2504.13171
Models pre-process persistent context during idle time, anticipating likely queries and pre-computing useful representations before the user asks anything. Delivers ~5x reduction in test-time compute at equal accuracy, up to 13-18% accuracy gains with more sleep-time scaling, and 2.5x per-query cost reduction when amortized across related queries. This paper seeded the consolidation-daemon pattern that both OpenAI and Anthropic productized as 'dreaming' in 2026.

### MemOS — memory as a scheduled operating-system resource (2025-07)
Source: https://arxiv.org/abs/2507.03724
Treats memory as a first-class managed resource, unifying plaintext, activation (KV-cache), and parameter-level memories under one scheduler with lifecycle management (generation, activation, archiving) via a MemCube abstraction. The open-source system (MemTensor/MemOS) claims large temporal-reasoning gains over baselines and ~35% token savings via cross-task memory reuse. Matters as the strongest articulation of 'memory governance' — versioning, scheduling, and migration — as an architectural layer rather than a bolt-on store.

### MIRIX — six-type multi-agent memory (Core/Episodic/Semantic/Procedural/Resource/Knowledge Vault) (2025-07-10)
Source: https://arxiv.org/abs/2507.07957
A meta-memory-manager routes each piece of incoming information to one of six typed stores, each with its own update and retrieval logic, coordinated by specialized agents. Achieved 85.4% on LOCOMO (then-SOTA) and 35% higher accuracy than RAG on multimodal ScreenshotVQA with 99.9% less storage. The evidence that segmenting memory by cognitive type (facts vs events vs procedures vs documents) beats one undifferentiated store.

### Memory-R1 and Mem-alpha — RL-trained memory management (2025-08 / 2025-09-30)
Source: https://arxiv.org/abs/2508.19828 and https://arxiv.org/abs/2509.25911
Both train the memory manager itself with outcome-driven RL instead of hand-written heuristics: Memory-R1 learns ADD/UPDATE/DELETE/NOOP operations plus an answer agent via PPO/GRPO from as few as 152 QA pairs; Mem-alpha trains construction across a core/episodic/semantic architecture with reward = downstream QA accuracy, and generalizes from 30k-token training to 400k+ token sequences (13x). Signals the field's verdict that what-to-store/update/forget decisions are learnable policies, and that heuristic pipelines (extract-then-embed) leave a lot on the table.

### ReasoningBank + MaTTS (Google) — strategy-level memory from successes AND failures (2025-09 (Google Research blog 2026-04-21))
Source: https://arxiv.org/abs/2509.25140
Instead of replaying raw trajectories, an LLM-as-judge labels each past task success/failure and distills it into a compact human-readable memory item (title, one-line description, actionable content) — failures become preventative guardrails, not just discarded. Memory-aware test-time scaling (MaTTS) generates parallel trajectories and self-contrasts them to distill more robust strategies. Up to +34.2% relative effectiveness and -16% interaction steps on WebArena/SWE-Bench; the flagship example of the storage→experience shift.

### ACE — Agentic Context Engineering: evolving playbooks without collapse (2025-10)
Source: https://arxiv.org/abs/2510.04618
Stanford/SambaNova/Berkeley show that letting an LLM iteratively rewrite its own memory/context document causes 'context collapse' (details erode) and 'brevity bias' (domain insight dropped for concision). ACE instead maintains context as an itemized playbook updated by small delta operations through Generator/Reflector/Curator roles — never wholesale rewriting. +10.6% on AppWorld agents, +8.6% finance reasoning, ~87% lower adaptation latency; the single most important negative result for anyone building LLM-maintained knowledge files.

### Anthropic memory tool + context editing (API), Skills, and Claude Code file-based memory (2025-08 beta (memory_20250818), GA by 2026)
Source: https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool
Claude's production memory is deliberately low-tech and file-shaped: a client-side /memories directory Claude manipulates with six file commands (view/create/str_replace/insert/delete/rename), auto-prompted to check memory before every task and assume interruption; paired with context editing/compaction it shows 84% token savings on long tasks. Claude Skills (Oct 2025) added three-level progressive disclosure — frontmatter always loaded (~dozens of tokens), body loaded on trigger, linked files on demand. Claude Managed Agents 'dreaming' (research preview 2026-05-19) adds a scheduled between-session process that reviews transcripts and memory stores, extracts cross-session patterns, merges duplicates, and curates memory — with optional human review before changes land.

### OpenAI ChatGPT 'Dreaming' memory architecture (2026-06-04)
Source: https://openai.com/index/chatgpt-memory-dreaming/
Replaces the manually curated saved-memories list with background synthesis that reads across years of chat history offline and maintains an editable natural-language memory summary; it proactively revises time-sensitive memories (e.g. 'you are going to Singapore in July' becomes 'you went to Singapore in July 2026'). OpenAI reports factual recall up from 67.9% to 82.8%, preference adherence 55.3% to 71.3%, accuracy-over-time 52.2% to 75.1%, with ~5x compute reduction. Confirms consolidation-during-idle plus a human-readable, human-editable memory artifact as the converged consumer design. Google's equivalent, Gemini Personal Context / 'Personal Intelligence' (2026-01-14), goes a different route: a periodically regenerated compressed user profile plus retrieval over connected Google services (Gmail, Photos, YouTube, Search).

### Temporal consolidation wave: TiMem and 'Beyond Dialogue Time' (2026-01)
Source: https://arxiv.org/abs/2601.02845 and https://arxiv.org/abs/2601.07468
TiMem consolidates conversational memory hierarchically across time scales — progressively abstracting older material while preserving critical detail, with each level retrievable independently. Beyond Dialogue Time builds a temporal knowledge graph memory index that explicitly separates event time from dialogue time so retrieval respects when things actually happened, preventing stale facts from contaminating answers. Together they show the 2026 consensus: temporal structure belongs in the memory index itself, not reconstructed at query time.

### User as Code — executable memory for personalization (2026-06-15)
Source: https://arxiv.org/abs/2606.16707
Represents the user not as retrievable text but as typed Python objects (state) plus functions (rules), built by a two-phase pipeline: an append-only fact log that periodically consolidates into code. Matches retrieval systems on plain recall (78.8% LOCOMO) but on aggregate/temporal questions ('how many international trips last year?') retrieval memory scores 6-43% while executed memory hits ~99%, and rules can fire proactively (e.g. allergy-interaction alerts). The sharpest demonstration that similarity retrieval fundamentally cannot do aggregation, counting, or rule-triggering — you need a structured, computable layer.

### Self-evolving memory architectures: EvolveMem, O-Mem, MemPro (2025-11 through 2026-05)
Source: https://arxiv.org/abs/2605.13941 (also https://arxiv.org/abs/2511.13593, https://arxiv.org/pdf/2606.00619)
EvolveMem argues adaptive memory requires co-evolving both the stored knowledge and the retrieval mechanism: it exposes the full retrieval configuration (scoring functions, fusion strategies, answer policies) as an action space, and an LLM diagnosis module reads per-question failure logs, identifies root causes, and proposes guarded config changes with automatic rollback — +25.7% on LoCoMo over the strongest baseline, with evolved configs transferring across benchmarks. O-Mem (Nov 2025) adds active user profiling with hierarchical persona/topic retrieval. The trend: the memory system itself becomes a self-tuning artifact, not a frozen pipeline.

### Evaluation reality check: LongMemEval-V2 and cross-scenario generality diagnostics (2026-05 / 2026-06-04)
Source: https://arxiv.org/abs/2605.12493 and https://arxiv.org/abs/2606.04315
LongMemEval-V2 (UCLA) reframes evaluation around 'experienced colleague' behavior — preference adherence, applying accumulated context to new tasks, temporal reasoning — and finds all current systems degrade sharply as information density rises. The cross-scenario diagnostics paper shows Mem0, Zep, and A-MEM generalize poorly outside the scenarios they were tuned on, and that a well-structured simple baseline is competitive. Meanwhile vendors race on the old benchmarks (Mem0 reports 93.4% LongMemEval with its 2026 token-efficient algorithm) — evidence of benchmark saturation and overfitting.

### Memory security and governance: lifecycle survey + Verifiable Memory Governance (2026-04 (v2 2026-06-11))
Source: https://arxiv.org/abs/2604.16548
Surveys attacks and defenses across a six-phase memory lifecycle (Write, Store, Retrieve, Execute, Share/Propagate, Forget/Rollback), characterizing memory threats as persistent, stateful, and propagating — a poisoned memory keeps attacking every future session. Core finding: security cannot be retrofitted at retrieval time; it must be anchored in storage-time provenance, versioning, and policy-aware retention (their Verifiable Memory Governance framework). Related work (MemGuard, arXiv 2605.28009; SSGM) targets contamination — wrong or stale memories compounding over time.

### Local-first markdown convergence: Basic Memory and Karpathy's LLM wiki pattern (2025–2026 (Karpathy post 2026-04))
Source: https://github.com/basicmachines-co/basic-memory and https://arxiv.org/abs/2603.07670 (surveys); Karpathy pattern coverage: https://codersera.com/blog/karpathy-llm-knowledge-base-second-brain/
Basic Memory derives a traversable knowledge graph purely from markdown conventions — frontmatter, categorized observations ([fact], [method]...), typed wiki-link relations ('pairs_well_with [[X]]') — with a rebuildable SQLite index, MCP tools, and memory:// graph-context URLs; humans edit in Obsidian, agents edit via MCP, same files. Karpathy's April 2026 LLM-wiki proposal independently converged on the same shape: an LLM 'compiles' (not summarizes) raw notes into a structured, interlinked markdown wiki with an index and log, no vector DB, relying on long context plus file navigation. Both validate plain markdown + agentic file ops as a frontier-competitive substrate, matching Anthropic's own /memories design.

### 2026 surveys codify the field: write–manage–read loop and storage→reflection→experience (2026-03-08 / 2026-05-07 (ACL 2026 Findings))
Source: https://arxiv.org/abs/2603.07670 and https://arxiv.org/abs/2605.06716
Du's survey frames agent memory as a write–manage–read loop over five mechanism families (context compression, retrieval stores, reflective self-improvement, hierarchical virtual context, policy-learned management), and names the open frontiers: continual consolidation, causally grounded retrieval, trustworthy reflection, learned forgetting, and write-path filtering. Luo et al. formalize the field's arc as Storage → Reflection → Experience — from preserving trajectories, to refining them, to abstracting generalizable knowledge — with proactive exploration and cross-trajectory abstraction as the current edge. Useful as the authoritative map of what 'state of the art' now means.

### DESIGN IMPLICATIONS
- Markdown files ARE the state-of-the-art substrate — this is no longer a compromise. Anthropic's production memory tool, Claude Code's MEMORY.md pattern, Basic Memory, and Karpathy's wiki all converged on plain files + agentic file operations (view/create/str_replace/insert/delete/rename). Build the engine as agent-editable markdown with exactly those six operations as the write API; you inherit git versioning, human editability, and zero lock-in for free.
- Ship a consolidation daemon ('dreaming') — this is the single highest-leverage 2026 idea and is trivially local. A scheduled offline pass (cron/launchd + one LLM batch call) that re-reads recent notes plus session transcripts, merges duplicates, resolves contradictions, rewrites time-sensitive entries ('is going' → 'went'), and updates indexes. Both OpenAI (June 2026) and Anthropic (May 2026) shipped exactly this; sleep-time compute shows ~5x query-time savings. Emit changes as a git diff for human review before landing — the review-gate flow Anthropic uses.
- Make facts bitemporal in frontmatter: every durable fact gets valid_from / valid_until (event time) plus recorded_at (ingestion time), and contradictions supersede rather than delete (add superseded_by links, keep the old entry). This is Zep/Graphiti's core mechanism and costs nothing in YAML; it makes 'what did I believe in March?' and 'what changed?' answerable — something no plain-notes tool does.
- Derive the knowledge graph from markdown conventions, never maintain a separate graph DB. Basic Memory proves typed wiki-links ('relation_type [[Target]]') plus categorized observation bullets give you a traversable graph with a rebuildable SQLite index as pure derived cache. Graph traversal from an entry point (2 hops along links) is your context-builder — cheaper and more explainable than embeddings for a personal-scale corpus.
- Never let the LLM rewrite whole memory files — ACE's context-collapse result is the key failure mode to design against. Structure notes as itemized entries with stable IDs and apply delta operations (add item, amend item, mark stale) via str_replace-granularity edits. Curation = dedupe and reorganize items, not re-summarize; brevity bias will silently destroy your best domain detail otherwise.
- Store distilled strategies, not just facts: add a ReasoningBank-style lessons layer where each completed task (from session transcripts) yields a memory item — title, one-line description, actionable content — extracted from failures as guardrails, not only successes. This is what upgrades the tool from a notes archive to an experience engine, matching the field's storage→experience arc.
- Adopt compile-not-summarize with a two-layer store: an append-only raw/ layer (clippings, transcripts, logs — never edited) and a compiled wiki/ layer the LLM restructures from raw with full detail, cross-references, and contradiction resolution. This is Karpathy's pattern and exactly mirrors User-as-Code's append-only-log → consolidated-state pipeline; the raw layer makes every compiled claim re-derivable and auditable.
- Add a computable typed-facts layer for aggregates: similarity retrieval scores 6-43% on questions like 'how many X last year?' while executed structured memory hits ~99% (User as Code). Locally: structured YAML/JSON blocks in notes (or a derived SQLite table of typed facts) that small scripts can count, filter, and date-range over. Optionally encode standing rules ('flag if a job lead is at an avoided company') as executable checks that fire proactively.
- Use Skills-style progressive disclosure for context economy: a root index (MEMORY.md) holding one-line descriptions of every note — a few dozen tokens each, always loadable — with bodies read on demand and linked files a further hop away. Enforce a frontmatter description: field on every note so the agent can route without opening files. This three-level layout is Anthropic's proven production design.
- Retrieval: start with BM25/ripgrep + link traversal + the index file, skip embeddings initially — the 2026 cross-scenario diagnostics show fancy memory frameworks generalize poorly and simple well-structured baselines are competitive at personal scale. But take EvolveMem's lesson: make retrieval config (scoring, k, fusion, traversal depth) a config file, log retrieval misses, and periodically let the consolidation pass propose config changes with rollback.
- Bake in provenance and rollback from day one (the memory-security survey's core finding: security must be anchored at write time). Every memory entry carries source (which conversation/document/URL) and recorded_at; the whole store is a git repo so any poisoned or wrong memory can be traced and reverted. Treat ingested third-party content (web clippings, emails) as untrusted: quarantine in raw/, only promote to wiki/ through the reviewed compile step.
- Implement forgetting as archival decay, not deletion: track last-accessed per note in the derived index, let the consolidation daemon demote stale never-accessed items to an archive/ tier (out of the index, still greppable). Learned forgetting is an open research problem — heuristic decay with full recoverability is the safe, frontier-consistent local answer.
- Evaluate like LongMemEval-V2, not like a recall benchmark: build a small personal eval set of aggregate questions, temporal questions ('what was true before X?'), preference-adherence checks, and stale-fact traps, and run it after each consolidation pass. This catches consolidation-induced regressions (the field's documented failure mode) and is what distinguishes a genuinely SOTA tool from a rehash.
- The genuinely novel combination — nobody ships all of these together locally: bitemporal markdown facts + delta-only curation + dreaming daemon with git-diff review + ReasoningBank lessons layer + computable typed-facts + progressive-disclosure index. Each piece is validated by 2025-26 frontier work; the integration over a plain markdown vault is the open niche.
